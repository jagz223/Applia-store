Aplify Store — Planificación y orden de desarrollo

Documento vivo para construir una página de venta de ítems con admin, pedidos, delivery, promociones y descuentos.

Enfoque: MVP → iteraciones Término clave: Pedido (no “carrito”) Delivery con Leaflet

Objetivo y alcance

Visión

Construir una plataforma para vender ítems donde los administradores puedan crear productos con precios y adicionales, armar promociones (grupos con precio menor), aplicar códigos de descuento, y permitir al cliente crear un Pedido con opción de Delivery, Para llevar o Comer en sitio (configurable).

Principio de planificación

Primero se construye un núcleo estable: catálogo + pedido + cálculo de precio. Luego se añaden descuentos/promos, logística (delivery), y finalmente mejoras “enterprise” (roles avanzados, auditoría, analíticas, etc.).

Roles, datos mínimos y decisiones

Base
  • Cliente: correo, teléfono, y dirección opcional guardable (para delivery).
  • Admin: crea ítems, adicionales, promociones, códigos de descuento, y tasa de cambio diaria.
  • Pedido: lista de ítems + adicionales + promos + descuentos + tipo (delivery / para llevar / sitio).
  • Monedas: precios en $ o €; conversión a Bs con valores diarios configurados por admin.

Decisiones a fijar temprano (para no re-trabajar)

  • Regla de “precio final”: orden de aplicación de promos, descuentos y delivery.
  • Compatibilidades: un ítem puede estar en promo y además tener código de descuento, ¿sí/no?
  • Modo multi-negocio: ¿una sola tienda o múltiples tiendas? (afecta el modelo de datos).

Orden recomendado de desarrollo (por fases)

Ruta crítica

Cada fase se implementa con entregables claros. Si una fase no está completa, la siguiente se vuelve cara de mantener. Prioridad: cálculo de precio consistente y datos bien modelados.

Fase 0

Fundación del proyecto

Bloquea todo

Definir base técnica y decisiones que afectan el modelo (evita refactors grandes).

Entregables

  • Modelo de datos (Ítem, Adicional, Promo, Descuento, Pedido, Usuario, Dirección, Configuración).
  • Reglas del cálculo de precio documentadas y testeables.
  • Navegación de pantallas “esqueleto” (Home/Catálogo, Detalle, Pedido, Checkout, Admin).

Riesgos a controlar

  • Reglas ambiguas de descuentos/promos.
  • Moneda/conversión mezclada con lógica de UI (debe quedar en un “motor” de precios).

Meta: que el “motor de precios” sea independiente y tenga pruebas.

Fase 1

MVP de venta: catálogo + pedido + checkout básico

Core

Que un cliente pueda armar un pedido y ver un total correcto (sin delivery aún).

Frontend (cliente)

  • Listado de ítems + búsqueda/filtros simples.
  • Detalle del ítem con selección de adicionales.
  • Pantalla “Pedido”: editar cantidades, remover ítems, ver subtotal.
  • Checkout: correo + teléfono; opción “guardar dirección” (si aplica luego).

Backend / datos

  • CRUD de ítems y adicionales (mínimo vía admin o seed temporal).
  • Crear pedido y persistirlo.
  • Motor de precios: subtotal por ítem + adicionales + total del pedido.
Fase 2

Admin real: gestión de ítems y tasas de cambio

Core

Que el negocio opere sin tocar código: inventario básico y conversión a Bs administrable.

Admin

  • CRUD de ítems: nombre, descripción, imágenes, moneda, precio base, estado (activo/inactivo).
  • CRUD de adicionales: precio incremental, compatibilidad con ítems.
  • Configuración: $→Bs y €→Bs (actualización diaria manual).

Precio y moneda

  • Mostrar precios en $/€ según ítem y su equivalente en Bs (si se requiere en UI).
  • Guardar valores “congelados” en el pedido (para que no cambie si la tasa se actualiza después).

Recomendación: almacenar montos en “minor units” (centavos) para evitar errores de redondeo.

Fase 3

Promociones y códigos de descuento

Valor comercial

Implementar precio inteligente: bundles más baratos y cupones por ítem/pedido/grupo.

Promociones (grupos)

  • Definir “bundle”: ítems requeridos + precio promo.
  • Reglas de aplicación: mejor precio automático vs selección manual.
  • Vista en el cliente: “Ahorra X con esta promo”.

Códigos de descuento

  • Tipos: porcentaje o monto fijo.
  • Alcance: ítem / pedido / promoción (grupo).
  • Restricciones: vigencia, usos máximos, mínimo de compra.

Meta: el motor de precios debe calcular “total” y “desglose” (por transparencia).

Fase 4

Delivery + Leaflet + cálculo de costo

Logística

Habilitar mapa, selección/guardado de dirección y costo de delivery sumado al total.

Cliente

  • Selector de tipo de pedido: delivery / para llevar / comer en sitio.
  • Mapa (Leaflet): pin de ubicación + dirección textual.
  • Opción “guardar dirección” para usos futuros.

Reglas de delivery

  • Cálculo por distancia (o zonas) + mínimo/máximo configurable.
  • Configuración para habilitar/deshabilitar cada modo (delivery / llevar / sitio).
  • Guardar el costo final del delivery en el pedido (auditabilidad).
Fase 5

Operación: estados del pedido, panel, notificaciones

Escalamiento

Pasar de “crear pedido” a “operar pedidos” (workflow real).

Flujo

  • Estados: creado → confirmado → en preparación → listo/en ruta → entregado/cancelado.
  • Panel admin para ver pedidos y filtrar por estado.
  • Historial del cliente (pedidos anteriores).

Notificaciones

  • Correo o WhatsApp/SMS (según disponibilidad) para confirmación.
  • Mensajes en pantalla con tracking del pedido.
Fase 6

Mejoras futuras (backlog)

Roadmap

Capas opcionales para robustez y crecimiento.

Producto

  • Variantes (talla/color), categorías avanzadas, inventario/stock.
  • Recomendaciones, favoritos, reseñas.
  • Multi-tienda/multi-sucursal.

Plataforma

  • Roles/permiso granular (admin, operador, repartidor).
  • Auditoría de cambios, logs y analíticas.
  • Pagos online, facturación, integraciones.

Checklist técnico recomendado (para evitar dolores)

Calidad

Motor de precios

  • Debe retornar total + desglose (subtotales, descuentos, delivery).
  • Pruebas: combos de ítems + adicionales + promo + cupón + delivery.
  • Guardar “snapshot” de precios/tasa de cambio dentro del pedido.

Seguridad y consistencia

  • Validaciones del lado servidor (no confiar en totales del cliente).
  • Permisos para endpoints admin.
  • Integridad: no permitir promos inválidas o cupones fuera de vigencia.
Sugerencia práctica

Si hay dudas sobre reglas (promos vs cupones), implementar primero “modo simple”: 1 promo + 1 cupón por pedido, con prioridad fija. Luego se expande.
