Visión y reglas de negocio

  • Tienda ≠ rol. Cualquier usuario autenticado puede ser dueño de una tienda (cliente, profesional o ambos). No reemplaza el rol de profesional ni el de cliente.
  • Mensualidad independiente. Si eres profesional pagas la de profesional y, si tienes tienda, la de tienda. Son dos suscripciones de visibilidad distintas.
  • Flujo sin bloqueo duro en creación. Se puede crear la tienda y ver la vista pública sin haber pagado; la gestión (tuerca) y la publicación en el catálogo quedan condicionadas al pago.
  • Ingredientes/materiales globales. Una sola colección compartida por todas las tiendas; los productos referencian ítems de esa colección.
  • Visibilidad cruzada (punto 14).
    • Sin mensualidad de tienda → tienda oculta en listado, sin acceso por link directo (pantalla «Tienda inactiva por el momento»).
    • Con tienda pagada pero sin mensualidad profesional → servicios del profesional ocultos en búsqueda (comportamiento ya existente vía computeListingPublished).

Prompt 1 — Fundamentos backend y contratos

Prioridad máxima Cubre bases de puntos 4, 7 (colección global) y habilita todo lo demás.

Objetivo

Dejar el «esqueleto» de tiendas en servidor y tipos compartidos, sin UI compleja.

Tareas

  • Añadir constantes de colección en FIRESTORE_COLLECTIONS.
  • Tipos Zod/shared: Store, StoreProduct, IngredientMaterial.
  • Métodos en storage-genfeb.ts / storage-firestore.ts: crear tienda, obtener por slug, por owner, listar tiendas activas (para fase 7).
  • API REST (ejemplo):
    • POST /api/stores — crear (auth)
    • GET /api/stores/mine — tienda del usuario
    • GET /api/stores/:slug — pública (respeta estado activo en fase 7)
    • GET /api/ingredients-materials?q=&page= — listado paginado 20, filtro por nombre
    • POST /api/ingredients-materials — crear global (auth; validar nombre único case-insensitive)
  • Slug único derivado del nombre + sufijo si colisión.

Texto sugerido para el asistente

Implementa el módulo backend de Tiendas en GenFeb según docs/MODULO_TIENDAS_PLAN_IMPLEMENTACION.html — Prompt 1.

Incluye colecciones Firestore (stores, store_products, ingredients_materials), tipos shared, storage y rutas API mínimas. Un usuario solo puede tener una tienda. Ingredientes/materiales son globales con paginación de 20 y búsqueda por nombre. No hagas UI todavía.

Criterios de aceptación

  • Se puede crear tienda vía API y leerla por slug y por dueño.
  • Ingredientes listables y creables sin storeId.
  • Tests manuales con curl o cliente REST documentados en comentario breve.

Prompt 2 — Mensualidad de tienda en configuración y estado de vigencia

Prioridad máxima Puntos 2, 4, 14 (lógica de activo).

Objetivo

Variable de precio en admin y campo visibilitySubscriptionEndsAt en documento de tienda, análogo al profesional.

Tareas

  • Slug store en SUBSCRIPTION_FEE_ADMIN_SLUGS + etiquetas en español.
  • subscriptionMonthlyUsdForProvider o función hermana subscriptionMonthlyUsdForStore() que lea la tarifa store.
  • Helper isStoreVisibilityActive(store, now) reutilizando isVisibilitySubscriptionWindowActive.
  • Endpoint GET /api/stores/subscription-quote → { monthlyUsd, label } para la pantalla de creación.
  • Al aprobar pago (Prompt 3) se extenderá endsAt; en esta fase dejar hook/listener preparado.
Según docs/MODULO_TIENDAS_PLAN_IMPLEMENTACION.html — Prompt 2: agrega mensualidad "Tienda" en admin (subscription-category-fees), lectura de precio USD y campo visibilitySubscriptionEndsAt en stores con helper isStoreVisibilityActive. Expón GET /api/stores/subscription-quote. Sin UI de pago aún.

Criterios de aceptación

  • Admin puede editar precio mensual de tienda como las demás categorías.
  • API de cotización devuelve el monto configurado.
  • Tienda sin fecha de fin se considera inactiva para catálogo (definir política explícita: sin pago = no publicada).

Prompt 3 — Pagos, administración y notificaciones

Alta Puntos 9, 10, 11, 12.

Objetivo

Mismo flujo de transferencia + comprobante que profesional/Marketplace, pero scoped a tienda.

Tareas

  • Nuevo paymentKind: store_subscription_transfer en metadata de transferencia / reporte (verification_fee o tipo dedicado store_subscription_fee — elegir uno y ser consistente).
  • POST /api/stores/:id/subscription-payment — subir comprobante (código, fecha, monto, archivo).
  • Página cliente /tienda/pago o /my-store/subscription: copiar layout de pago existente (QR bancario, datos transferencia, formulario comprobante).
  • Admin: nueva pestaña o subsección «Pagos tiendas» en Admin.tsx (filtrar transferencias por kind/storeId).
  • Aprobar → extender visibilitySubscriptionEndsAt N meses; rechazar → notificación + payload para abrir chat staff (reutilizar conversaciones soporte si existe, o canal staff genérico).
  • Banner en vista tienda dueño: «Activa tu tienda haciendo el pago correspondiente» con link a vista de pago (punto 9).
Implementa Prompt 3 del plan de tiendas: flujo de pago por transferencia/comprobante igual al de suscripción profesional, paymentKind store, aprobación/rechazo en admin, notificación al rechazar con opción de chat con staff. Incluye ruta de pago en cliente y banner de activación.

Criterios de aceptación

  • Dueño sube comprobante; admin aprueba/rechaza; al aprobar la tuerca podrá desbloquearse (Prompt 4).
  • Rechazo dispara notificación accionable.
  • UI de pago visualmente alineada con flujos de suscripción existentes.

Prompt 4 — Onboarding y vista pública (dueño vs visitante)

Alta Puntos 1, 2, 3, 9 (banner).

Objetivo

Recorrer el camino usuario: Configuración → Crear → Vista tienda, con tuerca bloqueada hasta pago.

Tareas UI

  • Settings + QuickSettingsPanel: botón destacado «Crear Tienda» (gradiente/icono Store). Si ya tiene tienda → «Mi tienda» / «Ver tienda».
  • /tienda/crear: formulario nombre; texto «Tener una tienda con objetos publicados cuesta USD {monthlyUsd}/mes» desde API quote; botón continuar sin exigir pago.
  • /tienda/:slug: vista pública placeholder de catálogo; esquina superior derecha botón tuerca (Settings icon) solo si user.id === ownerUserId.
  • Tuerca disabled + tooltip si !isStoreVisibilityActive; click en banner de activación → ruta de pago.
  • Registrar rutas en App.tsx.
Prompt 4 tiendas: botón vistoso "Crear Tienda" en Settings y QuickSettingsPanel, pantalla crear con nombre y precio mensual desde API, vista /tienda/:slug con tuerca solo para dueño bloqueada sin suscripción activa, banner a pago. Usa componentes shadcn existentes.

Criterios de aceptación

  • Cualquier usuario logueado ve el CTA en configuración.
  • Tras crear, redirige a su tienda.
  • Visitante no ve tuerca; dueño sí, bloqueada sin pago.

Prompt 6 — Productos e ingredientes/materiales

Media Puntos 6 y 7 completos.

Pantalla productos (punto 6)

  • Columnas: Nombre, Precio, Acciones.
  • Acciones: iconos ojo (vista/detalle), lápiz (editar), papelera (eliminar con confirmación).
  • API CRUD /api/stores/:storeId/products.

Crear / editar producto (punto 7)

  • Campos: nombre, descripción, precio, categorías opcionales (multi-select si ya hay categorías; si no, campo oculto hasta fase 8).
  • Toggle «¿Tiene ingredientes o materiales?» → muestra bloque de selección.
  • Combobox con búsqueda, paginación 20, botón + al lado.
  • Si el texto no tiene coincidencia exacta (normalizar trim + lower), habilitar + para crear en colección global y añadir a lista local.
  • Lista chips debajo con × para quitar de la selección del producto.
Prompt 6 tiendas: CRUD productos en panel admin (lista con ojo/editar/borrar) y formulario crear/editar con selector de ingredientes/materiales globales (paginación 20, filtro, crear con + si no hay match exacto). Backend store_products con array ingredientMaterialIds.

Prompt 7 — Catálogo público, navbar y visibilidad cruzada

Superficial / descubrimiento Puntos 13 y 14.

Tareas

  • Navigation: enlace «Tienda» / «Tiendas» → /tiendas.
  • Grid responsive de cartas cuadradas (CSS aspect-square), nombre como título, imagen default (/placeholder-store.png o avatar genérico).
  • GET /api/stores solo devuelve tiendas con isStoreVisibilityActive.
  • Acceso directo /tienda/:slug con suscripción vencida: mensaje «Tienda inactiva por el momento» (HTTP 200 con flag o 404 según producto — preferible 200 + UI clara para no filtrar slugs).
  • Profesional sin pago tienda: su tienda no aparece en grid ni es navegable.
  • Profesional con tienda pagada pero sin mensualidad pro: servicios ocultos (no tocar lógica existente de listing).
Prompt 7 tiendas: página /tiendas en navbar con grid de cartas, imagen default, API solo tiendas activas. Ruta pública inactiva muestra "Tienda inactiva por el momento". Respetar visibilidad cruzada profesional vs tienda según plan.

Fases diferidas (punto 8 — cuando indiques)

Implementar en prompts futuros separados, no mezclar con 1–7:

  • Categorías de tienda — CRUD + asignación múltiple en productos.
  • Promociones de tienda — reglas y vigencia.
  • Códigos de descuento de tienda — distintos de promotional_codes globales de plataforma.
  • Configuraciones de tienda — horarios, políticas, imagen de portada, etc.
Cada ítem anterior debe tener su propia colección Firestore y pantalla en el mismo shell del Prompt 5.
