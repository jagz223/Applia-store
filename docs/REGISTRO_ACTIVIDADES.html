1. Resumen ejecutivo del trabajo realizado

Tecnologías del proyecto

  • Frontend: React + TypeScript + Vite (carpeta client).
  • Backend: Express.js + TypeScript (carpeta server).
  • Base de datos principal prevista: PostgreSQL con Drizzle ORM.
  • Almacenamiento alternativo: memoria (in-memory) y soporte para Firestore.

Se verificó que la versión de Node del entorno es v24.11.1, compatible con el requisito del proyecto (Node 18+).

Configuración actual de entorno (.env)

  • DATABASE_URL=postgresql://... — ENABLE_DATABASE=false → la app no usa PostgreSQL, sino almacenamiento en memoria.
  • Con ENABLE_DATABASE=false los datos se pierden al reiniciar; con true se usaría PostgreSQL.

Revisión de esquemas (Drizzle / PostgreSQL)

Archivos analizados:

Conclusión: el sistema tiene un modelo de datos completo para usuarios, roles, catálogo, reservas, pagos, documentos, chat, notificaciones y reseñas.

Migraciones

No existen archivos de migración; solo npm run db:push (sincronización directa del esquema con la base).

5. Incidencia: error al inicializar Firebase

Síntoma

Error al inicializar Firebase: TypeError: Cannot read properties of undefined (reading 'cert')
    at initializeFirebase (server/firebase-admin.ts:50:36)

admin.credential era undefined, por tanto admin.credential.cert(...) fallaba.

Investigación

En firebase-admin v13 con ESM, import * as admin from "firebase-admin" no expone correctamente admin.credential. La forma correcta es el import por defecto: import admin from "firebase-admin".

Solución aplicada

En server/firebase-admin.ts se cambió:

// Antes
import * as admin from "firebase-admin";

// Después
import admin from "firebase-admin";

El resto del archivo se mantuvo igual. Tras reiniciar con npm run dev, se espera el mensaje: ✅ Firebase Admin SDK inicializado correctamente.

6. Uso de Firestore como base de datos y creación de colecciones

Con la conexión a Firebase operativa, se realizó lo siguiente:

6.1. Ampliación de colecciones en el código

En server/firebase-admin.ts se actualizó FIRESTORE_COLLECTIONS para incluir todas las entidades del sistema:

  • users, user_roles, categories, providers, services, service_addons, bookings, booking_addons, booking_statuses, taxes, coupons, escrow_payments, documents, conversations, messages, notifications, financial_reports, reviews, review_stats, mango_sync, payments, invoices.

6.2. Todo el almacenamiento en Firestore (sin híbrido)

  • Decisión: Toda la base de datos debe estar en Firestore; nada en memoria para producción.
  • En server/storage-firestore.ts se implementó el contrato completo IStorage: FirestoreStorageImpl implementa todos los métodos (usuarios, roles, categorías, proveedores, servicios, reservas, pagos escrow, documentos, conversaciones, mensajes, notificaciones, reportes financieros, sincronización ManGo, reseñas, estados de reserva, impuestos, cupones, add-ons, vouchers de pago, etc.) usando solo Firestore.
  • Se añadió un helper getNextId(collectionKey) con colección _counters para generar IDs numéricos de forma atómica (providers, services, bookings, etc.), ya que Firestore usa IDs de documento string por defecto.
  • En server/index.ts: cuando isFirebaseConfigured() es verdadero, se asigna setGenFebStorage(getFirestoreStorage()). Ya no se usa HybridStorage ni memoria para ninguna entidad; todo persiste en Firestore.

6.3. Roles persistidos en Firestore (buena práctica)

  • Los roles de usuario (admin, professional, client) y los datos de perfil (teléfono, dirección, ciudad, idioma, etc.) se almacenan en el documento del usuario en la colección users de Firestore.
  • En server/storage-firestore.ts, getUserRole(userId) y updateUserRole(userId, data) leen y actualizan ese documento, manteniendo una sola fuente de verdad.

6.4. Script para crear todas las colecciones en Firestore

  • Se añadió script/seed-firestore.ts: lee las credenciales del .env, inicializa Firebase y escribe en cada colección de FIRESTORE_COLLECTIONS un documento con id _seed (campos _seed, _createdAt, _note). Así todas las colecciones quedan creadas en la consola de Firebase.
  • En package.json se agregó el script: npm run seed:firestore. Es el único comando de seed necesario; no se requiere otro para roles, ya que el rol se guarda en el documento del usuario en la colección users.

Cómo dejar la base en Firebase con todas las colecciones:

  1. Tener el .env con las variables de Firebase correctas y el servidor mostrando ✅ Firebase Admin SDK inicializado correctamente.
  2. Ejecutar desde la raíz del proyecto: npm run seed:firestore.
  3. Revisar en Firebase Console → Firestore Database que aparezcan todas las colecciones (algunas tendrán solo el documento _seed, que se puede borrar después si se desea). Los usuarios que se registren o creen desde la app tendrán ya el campo role y el perfil en el mismo documento.

8. Seeders de roles y usuarios de prueba

Se crearon dos scripts independientes para poblar Firestore con roles por defecto y un usuario de prueba por cada rol.

8.1. Seeder de roles (npm run seed:roles)

  • Archivo: script/seed-roles.ts.
  • Inicializa Firebase, obtiene el storage de Firestore y llama a seedRoles().
  • Crea los roles por defecto solo si aún no existen (admin, professional, client) en la colección roles de Firestore.

9. Resumen de APIs del backend (GenFeb)

Endpoints principales que usa el front y herramientas externas. Todas las rutas bajo /api; las que requieren autenticación usan header Authorization: Bearer <JWT>.

  • Auth: POST /api/auth/register, POST /api/auth/login, GET /api/auth/me (JWT).
  • Catálogo (público): GET /api/categories, GET /api/providers, GET /api/providers/:id, GET /api/services, GET /api/services/:id.
  • Reservas: PATCH /api/bookings/:id/status (solo proveedor de la reserva, JWT).
  • Roles (definición): GET /api/roles, GET /api/roles/:code (JWT); POST /api/roles, PATCH /api/roles/:code, DELETE /api/roles/:code (JWT + admin).
  • Admin: GET /api/admin/users (JWT + admin) — listado con paginación (page, limit) y filtros (role, name, email, lastName).
  • El resto de rutas (facturas, PayPal, GenFeb reservas/chat/documentos/etc.) se registran en server/routes-genfeb.ts, routes-invoices, routes-paypal, etc.

10. Refactor arquitectónico: servicios, SOLID y código limpio

Se aplicaron mejoras para que el backend escale mejor, esté ordenado y cumpla con SOLID y arquitecturas limpias.

10.1. Segregación de interfaces (SOLID — Interface Segregation)

  • Archivo: server/storage-contracts.ts (nuevo).
  • Se definieron contratos por dominio: IUserStorage, IRoleStorage, ICatalogStorage, IBookingStorage.
  • Cada interfaz agrupa solo los métodos que un cliente (servicio) necesita; IStorage en storage-genfeb.ts ahora extiende estas cuatro y añade el resto del dominio (pagos, documentos, mensajes, etc.).

10.2. Capa de servicios de dominio

  • Carpeta: server/services/.
  • UserService (user.service.ts): getUsers, getUserById, getUserByEmail. Depende de IUserStorage.
  • RoleService (role.service.ts): ensureRolesSeeded, getRoles, getRoleByCode, createRole, updateRole, deleteRole. Delega en IRoleStorage y asegura que los roles por defecto existan.
  • CatalogService (catalog.service.ts): categorías, proveedores, servicios (get/create/seed). Depende de ICatalogStorage.
  • BookingService (booking.service.ts): reservas (get/create/update). Depende de IBookingStorage.
  • Los servicios reciben el almacenamiento por constructor; en services/index.ts se exportan instancias singleton que usan genFebStorage.

10.3. Rutas finas (thin routes)

  • Las rutas solo validan entrada (query/body) y delegan en servicios; la lógica de negocio está en la capa de servicios.
  • routes-admin.ts: GET /api/admin/users usa userService.getUsers(...).
  • routes-roles.ts: todos los endpoints de roles usan roleService (getRoles, getRoleByCode, createRole, updateRole, deleteRole).
  • routes.ts: categorías, proveedores, servicios y PATCH /api/bookings/:id/status usan catalogService y bookingService.

10.4. Unificación del almacenamiento en las rutas principales

  • Antes, routes.ts usaba storage de ./storage (Replit/legacy) para categorías, proveedores, servicios y reservas.
  • Ahora todas esas rutas usan catalogService y bookingService, que a su vez usan genFebStorage (Firestore o memoria según configuración).
  • Un solo punto de acceso a datos para el catálogo y las reservas expuestas en routes.ts; el resto de rutas (GenFeb, auth JWT, etc.) siguen usando genFebStorage donde corresponda.

Beneficios: responsabilidad única por capa, fácil de testear servicios, extensión sin modificar rutas existentes (Open/Closed), y dependencia invertida (rutas → servicios → contratos de almacenamiento).
