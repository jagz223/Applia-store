1. Resumen ejecutivo de los cambios documentados

Este documento describe el trabajo realizado a partir de la creación de las categorías de profesión para proveedores y todo lo implementado después en GenFeb: relación usuario–proveedor en Firestore, cambio automático de rol al convertirse en profesional, corrección de rol en conflicto 409, visibilidad del CTA «Convertirse en Profesional», un solo sistema de categorías (seeder, migración, Explore por categoría), la API GET /api/me/provider para que la pantalla de crear servicio funcione, el enlace «Crear servicio» en el menú, la categoría fija (no seleccionable) al crear servicio y las APIs completas de servicios (crear, editar, eliminar). En todo ello se aplicaron buenas prácticas (SOLID, código limpio) y una estructura en capas (contratos de almacenamiento, servicio de dominio, rutas finas).

En términos no técnicos: Se definieron tipos fijos de proveedor, se aseguró que al registrarse como proveedor el usuario pase a «profesional», se corrigió el rol de quienes ya tenían perfil, se ocultó «Convertirse en Profesional» para quienes ya son profesionales o administradores, se unificaron las categorías en una sola lista en la base de datos, se permitió acceder a «Crear servicio» desde el menú y que la categoría del servicio sea la del perfil del profesional, y se completaron las APIs para que los profesionales puedan crear, editar y eliminar sus servicios.

2. Categorías de proveedor (lista fija y uso en el sistema)

Qué se hizo

Se definió una lista única y controlada de categorías que puede tener un proveedor en la plataforma. Así se evita que se ingresen categorías arbitrarias y se mantiene coherencia en filtros y reportes.

Dónde está definido

  • Archivo: shared/provider-categories.ts.
  • Se definen códigos (por ejemplo technical_services, legal, financial, maintenance, delivery, marketplace, transport_taxi), etiquetas para mostrar al usuario (p. ej. «Servicios Técnicos», «Legales», «Financiero») y las profesiones asociadas a cada categoría (ingeniero civil, abogado/a, asesor financiero, etc.).

Base de datos

En el modelo de proveedores se añadió un campo opcional category (texto). En Firestore no hace falta «subir» un esquema: el campo aparece cuando se guarda el primer proveedor con categoría. Los proveedores antiguos pueden no tener el campo; el sistema lo trata como opcional.

Para no programadores: Cada proveedor puede tener ahora una «etiqueta» de categoría (técnico, legal, delivery, etc.) elegida de una lista fija. La base de datos guarda ese dato en cada ficha de proveedor.

APIs creadas o modificadas

  • GET /api/provider-categories — Devuelve la lista de categorías permitidas (código y nombre). La usa el frontend para mostrar el desplegable al crear o editar un proveedor.
  • GET /api/providers — Ahora acepta un parámetro opcional category para filtrar proveedores por categoría.
  • POST /api/providers — Crear proveedor; el cuerpo puede incluir category (validada contra la lista permitida). Requiere estar logueado (JWT).
  • PATCH /api/providers/:id — Actualizar proveedor (incluida la categoría). Solo el dueño del perfil o un administrador.
  • DELETE /api/providers/:id — Eliminar proveedor. Solo el dueño o un administrador.

Interfaz de usuario

En la página «Convertirse en Profesional» (/become-pro) se agregó un selector de categoría que se rellena con las opciones devueltas por GET /api/provider-categories. El usuario debe elegir una categoría de la lista al crear su perfil de proveedor.

3. Relación entre usuario y proveedor en Firestore

Firestore es una base de datos no relacional (NoSQL): no tiene «claves foráneas» como en una base SQL. La relación entre usuario y proveedor se hace por referencia en el código.

Cómo se relacionan

  • Colección users: cada documento es un usuario (identificado por su id).
  • Colección providers: cada documento es un proveedor y tiene un campo userId donde se guarda el id del usuario al que pertenece ese perfil.

Usuario → Proveedor: para saber si un usuario tiene perfil de proveedor, se busca en providers el documento cuyo userId sea el id de ese usuario (función getProviderByUserId(userId)).

Proveedor → Usuario: para mostrar datos del usuario (nombre, email, etc.) a partir de un proveedor, se usa el userId del proveedor y se lee el documento correspondiente en la colección users.

Para no programadores: No hay «tablas unidas» como en Excel. En su lugar, cada ficha de proveedor guarda el «número de usuario» al que pertenece. El programa usa ese número para ir a buscar los datos del usuario cuando hace falta. La relación la mantiene la aplicación al escribir y leer datos.

4. Cambio de rol a «profesional» al crear un proveedor

Regla de negocio

Cuando un usuario completa el formulario «Convertirse en Profesional» y se crea correctamente su perfil de proveedor, su rol en el sistema debe pasar a «professional». Así el sistema refleja que esa persona ya no es solo un cliente sino también un proveedor de servicios.

Implementación

  • En la ruta POST /api/providers (server/routes.ts), después de crear el proveedor con catalogService.createProvider(...), se llama a genFebStorage.updateUser(userId, { role: "professional" }).
  • El rol se guarda en el documento del usuario en la colección users de Firestore (o en memoria en desarrollo si no hay Firebase configurado).

Para no programadores: En el momento en que el sistema guarda tu perfil de proveedor, te marca automáticamente como «profesional» en la plataforma. No hace falta que un administrador cambie el rol a mano.

5. Ajuste cuando el usuario ya tiene proveedor (error «Ya tienes un perfil de proveedor»)

Problema que se resolvió

Algunos usuarios tenían ya un perfil de proveedor creado antes de que se implementara el cambio automático de rol a «professional». Esos usuarios seguían con rol «client» y podían volver a intentar crear otro proveedor; el sistema respondía con error 409 «Ya tienes un perfil de proveedor» pero no les actualizaba el rol.

Solución aplicada

En la misma ruta POST /api/providers, cuando se detecta que el usuario ya tiene un proveedor (y por tanto se devolverá el error 409), antes de responder se actualiza igualmente su rol a «professional». Así, aunque la respuesta siga siendo «ya tienes un perfil», el sistema corrige el rol en segundo plano.

  • Se mantiene el mensaje y el código 409 para que el frontend no cambie de comportamiento.
  • Una sola vez que el usuario (o un script) llame a «crear proveedor» con ese usuario, su rol quedará actualizado y en futuras visitas ya no verá el CTA «Convertirse en Profesional» si la interfaz lo oculta por rol.

Para no programadores: Si alguien ya tenía perfil de proveedor pero el sistema no lo había marcado como profesional, la primera vez que intente «crear» de nuevo (y reciba el aviso de que ya tiene uno), el sistema le actualizará el rol a profesional. A partir de ahí todo queda coherente.

6. Ocultar «Convertirse en Profesional» para profesionales y administradores

Regla de negocio

El botón o enlace «Convertirse en Profesional» solo debe mostrarse a usuarios que no sean ya professional ni admin. Es decir: se muestra a usuarios no logueados (para invitarles a registrarse y luego convertirse) y a usuarios con rol client.

Dónde aparece el CTA

  • Navegación (header): botón «Convertirse en Profesional» cuando el usuario está logueado y no tiene perfil de proveedor; si tiene perfil, se muestra «Dashboard» en su lugar.
  • Página de inicio (Home): botón en la zona de llamada a la acción (CTA).
  • Footer: enlace «Conviértete en Profesional» en la columna de enlaces de la plataforma.

En los tres lugares se aplica la misma regla: no mostrar el CTA si el usuario tiene rol professional o admin.

Para no programadores: Si ya eres profesional o administrador, no verás en ningún sitio el mensaje de «Convertirse en Profesional», porque ya no aplica a tu cuenta.

7. Código limpio y SOLID: una sola regla, hook y helpers reutilizables

Para no duplicar la lógica «quién ve el CTA» y mantener una única fuente de verdad, se centralizó la regla en funciones y un hook que usan todos los componentes.

7.1. Constantes y funciones en client/src/lib/auth-utils.ts

  • ROLES_HIDING_BECOME_PRO_CTA — Lista de roles que no deben ver el CTA: "professional" y "admin".
  • shouldShowBecomeProCTA(user) — Función pura que recibe el usuario (o null si no está logueado) y devuelve true si debe mostrarse el CTA. Devuelve false solo cuando el usuario está logueado y su rol es professional o admin.
  • hasAdminRole(user) — Indica si el usuario tiene rol admin. Se usa en la navegación para mostrar u ocultar el menú de administración (Admin Panel, Crear rol), sin depender del tipo exacto del usuario en el frontend.

7.2. Hook useShowBecomePro()

  • Archivo: client/src/hooks/use-show-become-pro.ts.
  • El hook usa useAuth() para obtener el usuario actual y llama a shouldShowBecomeProCTA(user). Devuelve un booleano.
  • Uso: en Navigation.tsx, Home.tsx y Footer.tsx se llama const showBecomePro = useShowBecomePro() y se muestra el botón o enlace solo cuando showBecomePro es verdadero.

Así, si en el futuro se cambia la regla (por ejemplo, añadir otro rol que no deba ver el CTA), solo se modifica ROLES_HIDING_BECOME_PRO_CTA o shouldShowBecomeProCTA; los componentes no tocan la lógica.

7.3. Tipado del usuario con rol (AuthUser)

  • La API de autenticación devuelve el usuario con un campo role. En el frontend, el tipo base User (compartido con el backend) no incluía role.
  • Se definió AuthUser en client/src/hooks/use-auth.ts como extensión de User con role?: string. Las funciones que obtienen el usuario logueado (fetchUser, login) y el retorno de useAuth() usan este tipo.
  • Para no acceder directamente a user.role en la navegación (y evitar problemas de tipado), el menú de administración usa hasAdminRole(user) en lugar de user?.role === "admin". La condición de visibilidad del CTA usa siempre useShowBecomePro().

Resumen de beneficios: una sola regla de negocio para «mostrar CTA» y «es admin», reutilización en navegación, home y footer, y tipado claro del usuario autenticado sin duplicar condiciones en los componentes (principios SOLID: responsabilidad única y abierto/cerrado).

8. Un solo sistema de categorías (servicios y proveedores)

Se unificó el sistema de categorías: las mismas categorías que se usan para clasificar servicios se usan para clasificar proveedores. Así hay una única fuente de verdad en la base de datos (colección categories en Firestore) y el formulario de «Convertirse en Profesional» usa la API de categorías en lugar de una lista hardcodeada.

8.1. Seeder de categorías

  • Archivo: script/seed-categories.ts. Comando: npm run seed:categories.
  • Lee las categorías por defecto desde shared/default-categories.ts (technical, legal, financial, maintenance, delivery, marketplace, transport) y las inserta en la colección categories de Firestore si no existen (por slug). Idempotente.
  • shared/default-categories.ts — Lista única con slug, name, type, icon para seed y para filtrar en Explore.

8.2. API de categorías para el formulario de proveedor

El formulario «Convertirse en Profesional» ya no usa GET /api/provider-categories (lista hardcodeada). Usa GET /api/categories, que devuelve las categorías guardadas en Firestore. Al crear un proveedor se envía categoryId (id numérico de la categoría) y opcionalmente category (slug) para compatibilidad.

8.3. Schema y almacenamiento

  • En shared/schema.ts se añadió categoryId (integer, opcional, referencia a categories.id) en la tabla providers. El campo category (texto) se mantiene para compatibilidad.
  • Storage (Firestore y memoria): createProvider y updateProvider aceptan categoryId. getAllProviders acepta filtro por categoryId. getProviderCategoryAvailability() usa las categorías de getCategories() y comprueba por categoryId (y por category slug si no hay categoryId) qué categorías tienen al menos un profesional.

8.4. Comando de migración

  • Archivo: script/migrate-provider-categories.ts. Comando: npm run migrate:provider-categories.
  • Para cada proveedor que tenga el campo category (string, p. ej. "technical"), busca en la colección categories un documento con ese slug y asigna su id al campo categoryId del proveedor. Así los proveedores existentes quedan alineados con el sistema unificado.

8.5. Vista Explore y servicios por categoría de proveedor

  • Explore (/explore): Las cartas de «Servicios por categoría» se construyen con las categorías devueltas por GET /api/categories, filtradas por los slug definidos en DEFAULT_CATEGORIES. La disponibilidad (encendida/apagada) viene de GET /api/provider-categories/availability, que ahora devuelve claves por id de categoría (no por código).
  • Al hacer clic en una carta de categoría disponible, se ocultan las cartas y se muestra la lista de servicios filtrada por esa categoría de proveedor. Se usa el parámetro providerCategoryId en la API de servicios.
  • GET /api/services acepta el query providerCategoryId (número). Devuelve solo servicios cuyo proveedor tiene categoryId igual a ese valor.

Para no programadores: Las categorías (técnico, legal, delivery, etc.) están guardadas una sola vez en la base de datos. Al crear un proveedor se elige una de esas categorías desde la misma lista que usa el resto del sistema. En «Explorar», al hacer clic en una categoría con profesionales disponibles, se muestran los servicios ofrecidos por esos profesionales.

9. API para obtener el perfil de proveedor del usuario logueado (GET /api/me/provider)

Problema que se resolvió

La pantalla «Crear servicio» (/create-service) necesita saber si el usuario que está logueado tiene un perfil de proveedor. Si lo tiene, muestra el formulario para dar de alta un nuevo servicio; si no, muestra el mensaje «You must be a provider to create services». Para eso el frontend llama a una API que devuelve el proveedor asociado al usuario actual. Esa API no existía en el servidor: la ruta no estaba registrada, por lo que la petición devolvía 404 («API route not found») y la pantalla asumía que el usuario no era proveedor aunque en Firestore sí tuviera perfil y rol «professional».

Solución aplicada

Se registró en el backend la ruta GET /api/me/provider:

  • Protegida con JWT: solo responde si el usuario envía un token válido en la cabecera Authorization: Bearer <token>.
  • Obtiene el userId del usuario autenticado (a partir del token) y llama a catalogService.getProviderByUserId(userId), que en Firestore busca en la colección providers el documento cuyo campo userId coincide con ese id.
  • Responde con el objeto del proveedor si existe, o con null si el usuario no tiene perfil de proveedor. El frontend usa ese resultado para decidir si mostrar el formulario de crear servicio o el mensaje de «debes ser proveedor».

Detalle para programadores: La ruta se registra al inicio de registerRoutes (en server/routes.ts), justo después de admin y roles, usando la ruta literal "/api/me/provider" para evitar conflictos con otras rutas y asegurar que Express la empareje antes que middlewares o rutas genéricas. No se duplica lógica: la responsabilidad de «buscar proveedor por userId» sigue en el servicio de catálogo (principio de responsabilidad única).

Para no programadores: El sistema ahora puede saber con certeza si tu cuenta tiene un «perfil de profesional» asociado. Si lo tienes, la pantalla de crear servicio se abre correctamente; si no, te indica que primero debes darte de alta como proveedor.

10. Acceso a «Crear servicio» desde el menú de navegación

Qué se hizo

La pantalla para crear un nuevo servicio (/create-service) existía y estaba definida en el enrutador de la aplicación, pero no había ningún enlace ni botón en la interfaz que llevara a ella. La única forma de llegar era escribir la URL a mano en el navegador.

Solución aplicada

  • En el menú desplegable «Servicios» del header (escritorio) se añadió la opción «Crear servicio», con icono, visible solo cuando el usuario tiene perfil de proveedor (providerProfile). Así, los profesionales ven la opción junto a «Todos los Servicios» y «Reservas».
  • En el menú móvil (menú hamburguesa) se añadió el mismo enlace «Crear servicio», también condicionado a que el usuario tenga perfil de proveedor, para mantener la misma experiencia en móvil.

Detalle para programadores: Se usa el mismo dato que ya proporciona useCurrentProvider() en la navegación (que a su vez llama a GET /api/me/provider). La condición providerProfile && (...) evita mostrar el enlace a usuarios que no son proveedores. No se añade lógica nueva de negocio; solo se reutiliza el estado «tengo perfil de proveedor» ya disponible en el componente (principio DRY).

Para no programadores: Si eres profesional, en el menú «Servicios» verás la opción «Crear servicio» para publicar un nuevo servicio sin tener que recordar la dirección de la página.

11. Categoría del servicio tomada del perfil del proveedor (no seleccionable)

Regla de negocio

Al crear un servicio, la categoría del servicio debe ser la misma que la categoría del perfil del proveedor que lo ofrece. Así se mantiene coherencia: un profesional de «Servicios Técnicos» solo ofrece servicios dentro de esa categoría. El usuario no debe poder elegir otra categoría en el formulario.

Implementación

  • En la página Crear servicio (client/src/pages/CreateService.tsx) se eliminó el desplegable (Select) de categoría. En su lugar se muestra un bloque de solo lectura con el nombre de la categoría del proveedor (obtenida a partir de provider.categoryId o, si no existe, de provider.category slug, buscando en la lista de categorías de la API).
  • El valor de categoryId del formulario se rellena en un useEffect con la categoría resuelta del perfil del proveedor. Al enviar el formulario, ese categoryId se envía al backend; el usuario no puede cambiarlo desde la interfaz.

Detalle para programadores: Se usa useMemo para resolver la categoría a partir de providerCategoryId o providerCategorySlug y la lista categories de useCategories(), de modo que se soporta tanto el modelo actual (proveedor con categoryId) como el legado (solo category como slug). El campo del formulario sigue siendo categoryId para cumplir el esquema de la API, pero el control se renderiza como un div de solo lectura con estilos de campo deshabilitado, sin opción de edición.

Para no programadores: Cuando creas un servicio, la categoría que aparece (por ejemplo «Servicios Técnicos») es la de tu perfil de profesional y no se puede cambiar en esa pantalla. Así todos tus servicios quedan clasificados en la misma categoría que tu perfil.

12. APIs completas de servicios: crear, editar y eliminar

Contexto

El frontend ya tenía la pantalla de crear servicio y llamaba a POST /api/services, pero esa ruta no estaba implementada en el servidor, por lo que devolvía 404. Tampoco existían rutas para editar (PATCH) ni eliminar (DELETE) un servicio, necesarias para que los profesionales puedan gestionar su oferta y para que los administradores puedan dar soporte.

APIs implementadas (sin duplicar las ya existentes)

Servicios — lo que ya existía:

  • GET /api/services — Listar servicios (con filtros opcionales: categoryId, search, providerCategoryId). Público.
  • GET /api/services/:id — Ver un servicio por id. Público.

Servicios — lo que se añadió:

  • POST /api/services — Crear servicio. Requiere JWT. Solo usuarios que tengan perfil de proveedor. El providerId y la categoryId se fijan en el backend a partir del perfil del usuario (no se confía del cuerpo de la petición). El cuerpo incluye title, description, price, imageUrl, y opcionalmente categoryId (si no se envía, se usa la del perfil del proveedor). Si el perfil no tiene categoría válida, se responde 400.
  • PATCH /api/services/:id — Actualizar un servicio (campos opcionales: title, description, price, imageUrl, isActive, categoryId). Requiere JWT. Solo el dueño del servicio (el proveedor cuyo id coincide con service.providerId) o un usuario con rol admin.
  • DELETE /api/services/:id — Eliminar un servicio. Requiere JWT. Misma regla de autorización: solo dueño o admin. Responde 204 sin cuerpo.

Proveedores / profesionales (ya existían, no se duplicaron)

Para referencia, las APIs de proveedores que ya estaban y se mantienen son: GET /api/providers, GET /api/providers/:id, GET /api/me/provider, POST /api/providers, PATCH /api/providers/:id, DELETE /api/providers/:id (estas dos últimas solo dueño o admin).

Implementación en capas (SOLID / clean code)

  • Contrato de almacenamiento (server/storage-contracts.ts): se definió el tipo ServiceUpdate (campos editables del servicio) y se añadieron al contrato ICatalogStorage los métodos updateService(id, data) y deleteService(id). Así la capa de rutas y el servicio de dominio no dependen de la implementación concreta (Firestore o memoria).
  • Storage Firestore (server/storage-firestore.ts): implementación de updateService (lectura del documento, aplicación de campos enviados, update en el documento) y deleteService (borrado del documento). Se evita sobrescribir el documento entero; solo se actualizan los campos recibidos.
  • Storage memoria (server/storage-genfeb.ts): se implementaron las mismas firmas para cumplir el contrato; en memoria los servicios no se persisten en este flujo, por lo que devuelven undefined / false según corresponda.
  • Servicio de dominio (server/services/catalog.service.ts): updateService y deleteService delegan en el storage; no contienen lógica de negocio adicional, solo orquestación.
  • Rutas (server/routes.ts): validación del cuerpo con Zod (esquemas createServiceBodySchema y updateServiceBodySchema), comprobación de JWT, obtención del proveedor del usuario para autorización y para fijar providerId y categoryId en la creación. Las rutas permanecen «finas»: validan, autorizan y delegan en catalogService.

Para no programadores: Los profesionales pueden desde la aplicación crear nuevos servicios, editarlos y eliminarlos. Solo el dueño del servicio (o un administrador) puede modificarlo o borrarlo. La categoría del servicio se asocia correctamente al perfil del profesional.
